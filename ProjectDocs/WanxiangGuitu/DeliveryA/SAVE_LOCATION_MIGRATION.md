# 万象归途：Windows 存档定位迁移

格式仍为 **v9**；本批只增加存档定位层，不改变装备来源、死亡保护、收益分配或唯一结算规则。v1～v8 原兼容链、迁移前原始档案继续保留。

## 位置与入口

Company Name 仍为 DefaultCompany。Windows 通过 `Application.persistentDataPath` 动态取得当前用户位置：

- 旧：`%USERPROFILE%/AppData/LocalLow/DefaultCompany/BallMaze/ForestRuins`
- 新：`%USERPROFILE%/AppData/LocalLow/DefaultCompany/万象归途/ForestRuins`

普通启动和编辑器非 batch 试玩在读取/新建档前调用定位层。自动规则测试不走真实用户路径，使用显式 `InitializeLocatedStorage(old, new)`。产品也支持 `-wanxiang-storage-root "绝对隔离根目录"`，此时仅使用该根下 `Legacy/ForestRuins` 与 `WanxiangGuitu/ForestRuins`。参数缺失或非绝对路径会阻止初始化，不回退到真实档。

## 发布协议

1. 检查新旧目录证据（含异常文件）。只有两边均无证据才能初始化新档。
2. 仅有旧档时，先以只读入口验证可恢复主/备档、原有格式兼容及引用页面。主档有效而备份/其引用页不完整时阻止迁移；主档损坏但备份完整可按既定备份恢复策略继续。仍保留损坏原主档字节，不冒充主档完整。
3. 对整个旧目录建立 SHA256 清单，复制主档、备份、ground-loot 和必要迁移档案等所有普通文件；只排除未发布 `.tmp` 与本定位层自己的回执。禁止链接资源。`save-*.json` 档案也检查校验和，v9 档案检查分页。
4. 写入目标旁 `.migration-staging`，逐文件 Flush(true)，校验复制哈希、源未变化、完整存档集合。写回执后，以同卷 Directory.Move 发布目标。失败保留源与 staging，不创建空档。
5. 重试时把未完成 staging 改名为 `.interrupted-随机ID` 留存，重新复制并验证。已发布且回执匹配时直接继续新版；不重建 Run、不重抽奖励、不再次提交结算。

## 冲突与恢复

两边独立有档时不覆盖、不拼接。显示旧/新解析位置，可“重新检查”、明确“继续新版，保留旧档”或退出。选择新版仅在其可恢复时可用，并记录源指纹；若之后旧集合变化则再次提示。当前界面没有“覆盖新版改用旧档”按钮。需要改用另一套档时先退出并完整备份两边，由用户明确处理整套目录后再重试，勿只挪 JSON。

已迁移新档后来损坏时按既有主备恢复规则处理；不得因新档异常就把旧 Run 当新局重发收益。迁移本身只复制/验证，`InitializeStorage` 才执行原版本迁移与加载。读取检查不会在旧目录新建迁移档案。

## 分页保留与限制

页面先写入、主档再原子发布；写入失败不删除玩家物品或自动拾取。没有引入垃圾回收，也没有宣称磁盘使用有上界。主/备档、历史迁移档及中断 staging 都可能持有页面；本轮全部保留，磁盘会增长。空间/权限不足会阻止发布并允许修复后重试；用户应备份完整文件夹后处理磁盘空间。今后清理需独立实现引用集合校验。

## 已执行隔离检查

v8 与 v9 各覆盖营地、在途、Pending、Committed 四状态；主档坏备份好、备份引用页缺失、分页损坏、复制/发布边界注入、重复迁移、独立冲突及显式选新版。比较身份、装备实例与原始集合，重复提交不增收益；另有独立 Windows 游戏进程恢复。实际结果见 REPORT 与 Evidence。所有故障目标均为测试生成/合成目录，未读取或改动真实玩家存档。
