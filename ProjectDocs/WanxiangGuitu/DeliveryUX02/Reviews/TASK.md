# 万象归途玩家体验改进计划：UX-02 与 COMBAT-02

仓库：`https://github.com/mizunagare/BallMaze`

本计划基于用户提供的 Unity Game 截图与已审阅的部分 main 源码。截图是局部体验证据，不等同于完整运行复现。每批开工必须重新核对远端 SHA 和实际代码，不得假定旧版本仍是最新。

## 一、设计评审

四项反馈归纳为三个具体缺陷和一个战斗设计方向：

1. 敌人死亡后模型仍留在场景中，视觉上像站立的尸体或未死亡敌人，削弱战斗反馈。
2. 制作界面同时呈现配方分类、品质、物品类型、前置解锁、材料成本、仓库提示和追踪按钮，信息层级分散；营地仓库材料还要求手动取到背包，制造流程多了一步没有决策价值的搬运。
3. 更换胸挂/背包时，当前穿戴物、候选物和属性/容量差异不够直观，玩家难以判断“当前穿什么、换上后损失什么、哪个适合本次出征”。
4. 剑与枪需要从实际命中几何、动作时序、攻速和伤害形成清楚差异。当前源码中剑使用 `hero.AttackRange`，枪使用约 `3.8m + ReachBonus` 的近战筛选并叠加横向宽度限制；需要用真实配置与同条件测试确认差异，不只凭字段名称判断。

**开发顺序：**
- 第一批 `UX-02`：修复死亡模型残留，并简化制作和容器更换界面。
- 第二批 `COMBAT-02`：先测量四武器实际定位，再差异化剑/枪。
- 不将四项混成一次大规模重构；每批固定 SHA、限定范围、交付证据并暂停复审。

## 二、UX-02：死亡表现、制作与容器装备可视化

### UX02-00 开工条件

- 读取远端 `main` 并记录完整 SHA；若用户代码或远端基线已前进，停止并确认新基线，不 reset、不覆盖。
- 审计 `CombatEnemy`、`CombatHealth`、`FantasyActorVisual`、`CatInventoryPresenter`、`WorkbenchView`、`CampInventoryView`、`AdventureRecipes`、`AdventureLoadout`、`CampRuntime` 和仓库/制造事务。
- 记录用户场景、`ProjectSettings`、未提交修改、真实存档与现有 v9 合同的哈希/状态。使用隔离工程和合成存档。
- 不升级 Unity/URP/依赖，不新增 CI，不改变掉落、经济、随机流、结算合同或 v9 存档结构。

### UX02-01 敌人死亡后的模型处理

#### 当前问题
`CombatEnemy.Update()` 的死亡分支会停用 `CharacterController`、关闭预警环并调用 `DropLootOnce()`；但带 `FantasyActorVisual` 的敌人不会走简化模型的缩放收尾。`FantasyActorVisual` 继续播放死亡动作并保留模型，可能导致死亡模型长期留在场景中。Codex 必须在固定场景复现确认，不可仅按代码猜测。

#### 目标
- 死亡后立即停止 AI、攻击、碰撞移动和预警。
- 播放一次完整、可读的死亡动作；动作完成后隐藏或移除可见模型，并清理模型专属特效。
- 奖励/掉落结算完成前保留必要的逻辑身份；不可为隐藏模型提前销毁根对象导致 `DropLootOnce()`、首领奖励、经验或掉落丢失。
- `DropLootOnce()` 必须幂等；重复 Update、重复死亡回调、重置或恢复不能重复发奖励。
- 普通敌人、精英、普通 Boss/森林 Boss 使用明确生命周期策略。若首领需要保留残骸，按现有设计处理，不一刀切。
- 如需尸体短暂留存，时长配置化且有上限，避免死亡模型无限积累。
- 不改变生命、伤害、经验、掉落概率、随机流或结算逻辑。

#### 验收
1. 普通敌人、精英、普通 Boss/森林 Boss 分别验证。
2. 死亡动作只播放一次，结束后不留站立模型、攻击碰撞或警告环。
3. 每个敌人的奖励、经验、掉落只结算一次。
4. 连续击杀后可见死亡模型和临时特效数量有界。
5. 重置遭遇、重新进入区域和存档恢复不会产生重复掉落或遗留模型。
6. 保留修复前/后相同机位证据和受影响回归。
7. 自动化截图不代替人工审美验收。

### UX02-02 制作界面：左侧配方、右侧工作台

#### 目标布局
参考 Minecraft 工作台的信息层级，不照搬其资产或 UI：

- **左侧配方列表：**分类、搜索/筛选、图标、名称、品质/解锁状态；明确区分未解锁、缺料、可制作。默认展示当前阶段有意义的分类，减少重复的类型/品质按钮堆叠。
- **右侧制作工作台：**选中配方的大图标/名称、用途、产物预览、前置条件、材料明细、可制作数量、制造按钮和缺料提示。
- 材料缺口按真实可用材料逐项展示“需要/可用/缺少”，不要把所有信息塞进一段文字。
- 制作成功后展示产物、消耗和放置位置；空间不足要说明原因，不扣费。
- 保留配方解锁、前置依赖、品质、制造事务和追踪目标规则；布局层不直接修改库存。

#### 营地材料访问规则
玩家不应为了制造而逐个执行“从仓库取材料到背包”的无意义搬运。

先审计数据模型，再实现营地统一材料视图和原子事务：
- 营地制造可用材料 = 背包中可用于制造的材料 + 营地永久仓库中可用于制造的材料。
- 制造前一次性验证全部材料与产物空间；提交时原子扣除，默认先扣背包，再扣仓库。若现有业务合同规定不同，先记录差异和理由。
- 制造失败、保存失败或事务冲突时，不能部分扣费或重复生成产物。
- 仓库材料保留永久来源身份；当前 Run 未结算战利品、地面掉落或待领取奖励不能伪装成永久材料。
- 只有营地且 Profile/仓库状态已就绪时允许使用仓库材料；冒险中仍禁止直接访问。
- 查询和预览不得移动物品、生成物品或写存档。
- 不新增 v9 字段；优先复用 `CampRuntime`、`AdventureRecipes` 与现有制造事务。

#### 验收
1. 左侧配方列表可筛选，选中后右侧详情一致。
2. 未解锁、前置缺失、缺材料、可制作、空间不足状态清楚。
3. 材料只在营地仓库中也能制造，不要求先取进背包。
4. 背包与仓库混合支付可核对来源与前后数量。
5. 材料不足、空间不足、重复点击、保存失败、重复提交不产生部分扣费或重复产物。
6. 冒险中不能访问仓库；待结算/未领取/RunLoot 不能被错误消费。
7. 配方解锁成本只扣一次；已解锁后制造不重复扣解锁费用。
8. 旧仓库、旧 v9 存档、配方和制造回归通过。

### UX02-03 胸挂/背包更换：当前与候选直接对比

#### 目标布局
采用“当前装备—候选装备—差异”结构：
- 明确显示当前穿戴胸挂和背包，不让玩家从列表猜当前装备。
- 当前装备与候选装备并排显示图标、名称、品质颜色、格子布局与属性。
- 用“当前 → 更换后 / 净变化”显示差异；同时使用文字和图标，不能只靠背景颜色。
- 展示容量宽×高、可用/已占格数、溢出数量、攻击/防御/移动/采集等真实且相关的属性。
- 角色或纸娃娃区域在左侧；右侧为胸挂/背包槽位与候选列表。参考用户给出的三角洲装备页的信息层级，但保持项目自己的黑猫风格。
- 支持点击比较/装备；若支持拖动交换，点击仍须是完整可用的替代方式。
- 装备前预览旧容器物品的处理方式。若替换导致空间不足/物品溢出，列出受影响物品与去向并要求确认；禁止静默丢弃或删除。
- 穿戴容器不能当普通格子物品重复放入背包；装备变更走现有 `AdventureLoadout`/容器事务。

#### 验收
1. 首次打开即看出当前胸挂和背包。
2. 选择候选后显示容量、格子和属性的真实差异。
3. 不同容量与防御/移动取舍呈现正确。
4. 点击更换和拖动更换（若实现）走同一业务事务。
5. 溢出、空间不足、取消、保存失败和重复点击不丢物、不重复交易。
6. 装备后角色页、背包页、制造页、HUD属性及下一次出征状态一致。
7. 分辨率/UI缩放下不裁切，不遮挡关键确认按钮；静态截图不能替代操作回归。

### UX02-04 范围控制与交付
- 不重做全部七个导航页，不换 UI 框架，不引入外部 UI 库。
- 不重写整个库存系统；优先复用 `CatInventoryPresenter`、`AdventureLoadout`、`CampRuntime` 和现有事务。
- 交付 `REPORT.md`、`ACCEPTANCE.md`、`TESTING.md`、`Evidence/INDEX.md`，附同机位前后证据、材料核账、装备对比数据、死亡/掉落回归。
- `DEVELOPMENT_PLAN.md` 只增量更新状态和证据，不覆盖历史。
- 保留失败、超时、`NOT_RUN`、`UNRESOLVED`。推送后核对远端 SHA 并暂停复审。

## 三、COMBAT-02：四武器定位与剑/枪差异化（后续独立批次）

### COM02-01 先建立实际基线
审计 `AdventureCombat`、`ThirdPersonHero`、`AdventureLoadout`、`WeaponTraits`、`HeroProgression`、`FantasyActorVisual` 和相关测试。用同一敌人、同一装备品质、同一距离/朝向记录：
- 剑/枪普攻间隔、前摇/释放/恢复时长、有效命中形状和距离。
- 技能范围、方向、攻击段数与命中数量。
- 不同距离、侧向偏移、敌人多 Collider 时的命中结果。
- 单次伤害、DPS、打断能力、受击风险和操作容错。
- 同一场景下各武器击杀耗时、受到伤害、空挥率和实际命中率。

不能把字段名当作测量结果。所有测试条件、种子、敌人状态与武器数据必须固定并记录。

### COM02-02 初步设计方向
以下是需要通过实验验证的设计目标，不是未经测试就直接写死的最终数值：

- **剑：**中近距离、较宽的弧形/扇形命中，较快攻击循环，单次伤害较低，较高的连续输出与容错。
- **枪：**更长、更窄的前方刺击/直线判定，攻击间隔更长，单次命中伤害更高；侧向目标应更容易躲开，站位和朝向更重要。
- 长枪的有效前刺距离应明显超过剑，而不只是略微增加半径。作为首轮可测目标，枪的有效纵向距离可先试剑的约 1.4–1.6 倍，横向容差明显小于剑；最终范围由真实模型尺度和测试确定。
- 攻速和伤害应共同平衡。可先将枪的普攻间隔设为剑的约 1.2–1.4 倍，并尝试较高的单次伤害，再根据同条件 DPS、空挥率、受伤风险和击杀时间调整。不要只保证纸面 DPS 相同；长距离与窄判定本身是枪的优势和代价。
- 剑技能继续强调旋风/横扫；枪技能强调前刺/穿刺。除非现有动画或命中合同有阻断，不在本批重做动画系统。

这些比例是实验起始区间，不是平衡结论。先测量当前值，之后每次只改变有限参数，保留对照结果。

### COM02-03 扩展至四武器定位
在剑/枪差异通过验证后，再检查：
- 法杖：远程、弹道/范围伤害、较低近身容错。
- 弓：远程、多发/扇形、单发与总覆盖的取舍。
- 每种武器都有明确优势、代价和适用场景，不要求四者所有指标相同。
- 不通过单纯增加血量或无差别提高伤害制造差异。

### COM02-04 验收
- 剑与枪在同条件测试中，距离/角度命中图形有明显且可复现的差异。
- 枪在更远的正前方能命中而剑不能；枪的侧向目标更容易避开，剑的横扫更能覆盖近身侧向目标。
- 攻速、单次伤害、DPS、空挥率、受伤风险与击杀时间均有数据。
- 四武器差异通过至少固定条件自动化测试和独立试玩反馈交叉验证；样本不足时只报告趋势，不声称已完全平衡。
- 不改变经济、掉落、随机流、地图或 v9 存档合同。
- COMBAT-02 只有在 UX-02 完成审核后再开工，避免多批并行造成难以定位回归。
