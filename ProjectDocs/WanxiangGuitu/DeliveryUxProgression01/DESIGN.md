## 0. 设计命题

当前候选版本**已经能玩通**：三地区、七武器、八技能、制造、结算、跨进程恢复都经过真实 Player 验证。
问题不在功能，而在**意义**：玩家每一局都能做事，但说不清"这局为什么来、做到什么算成功、下一局该干什么"。
产品自己的 HUD 就写着"暂无主线成果"（`AdventureFlow.UI.cs:21`）。

因此本设计的命题是：

> **不新增系统，把已有系统接成"目标—路线—达成—下一目标"的闭环，并让玩家在三个时间尺度上都能回答一个问题。**

| 时间尺度 | 玩家必须能回答 | 对应界面 |
|---|---|---|
| 出征前 30 秒 | 我这局去哪、为什么去、带什么 | 出征准备 + 目标卡 |
| 局内 10 分钟 | 我现在离成功还差什么 | HUD 目标卡 + 路线页 |
| 结算后 60 秒 | 我下一步该做什么 | 结算页"下一局三件事" |

### 0.1 设计不变量（硬约束）

| # | 不变量 | 含义 |
|---|---|---|
| I1 | 零经济改动 | 材料产出、掉落概率、宝箱概率、配方成本、结算得失一律不变 |
| I2 | 零随机流改动 | 任何新判定**不得**消耗 `AdventureRandom` 的 Rewards/Placement/Events 流，否则会移动既有存档的可复现结果 |
| I3 | 零战斗数值改动 | 武器伤害、技能冷却、护甲减伤、经验曲线不动 |
| I4 | 零 v9 语义改写 | 只允许"向后兼容新增字段"，且必须单独决策（D-15）；不得改变既有字段含义 |
| I5 | 只读推导 | 目标进度必须能从 `RunState`/`ActiveRun.checkpoint`/场景对象**现算**，不新增写路径 |
| I6 | 不重做已有 | 路线评分、缺口计算、配方事务、结算规则、引导漏斗全部复用（见审计 §8） |

> 结论：**本设计的 P1 阶段可以做到"零 schema、零经济、零随机、零数值"**，只增加信息层与目标契约。

## 1. 玩法循环

三层结构：**单局状态机**（下）+ **元循环**（上）+ **五个嵌套时间环**（右）。完整图见 [LOOP_DIAGRAM.svg](LOOP_DIAGRAM.svg)。

### 1.1 单局状态机（已实现，不改）

```
营地整备 ──出征准备(地区+目标)──> 出征(RunState 落盘) ──> 探索/战斗/采集
   ^                                                        │
   │                                                        ├─> 撤离引导 5s（默认 duration=5, range=3）
   │                                                        │      └─ 受击/离开范围/再按 H 取消
   │                                                        └─> 死亡 / 主动放弃
   │                                                                 │
   └──── 结算（成功：带回本局；失败：归还入场、丢失本局、清等级）<──┘
                              │
                     制造 / 铭刻 / 领待领取 / 选下一目标
```

### 1.2 五个嵌套环与时长预算

| 环 | 典型时长 | 玩家决策 | 失败成本 | 现有支撑 |
|---|---|---|---|---|
| R1 交战 | 5–15 s | 普攻/技能/翻滚/切武器 | 掉血、药水 | `AdventureCombat`、`WeaponSkillExpansion` |
| R2 单局 | 8–15 min | 去哪、打不打、何时撤 | 本局所得 + 局内等级 | `AdventureFlow`、`AdventureRules` |
| R3 装备目标 | 2–5 局 | 追哪件、缺什么、走哪条线 | 时间 | `CraftingTargets`、`RouteScoring` |
| R4 地区精通 | 5–15 局 | 先啃哪个地区 | 时间 | `RuinsSpecialRewards`、`ForestBossRules` |
| R5 收藏完成 | 长期 | 还差哪几个藏品/配方 | 时间 | `specialRewards`、`unlockedRecipes` |

**设计意图**：R2 的失败成本必须"疼但可恢复"（现状正确：入场装备保护 + 本局清零）。
R3/R4 必须提供**确定性进度**，否则 R2 的随机失败会让人放弃——这正是当前最薄弱的一环。

## 3. 出征目标系统

### 3.1 目标 = 契约，不是文案

现状：`ExpeditionGoal` 三值已存在并写进 `RunState.goal`（`AdventureState.cs:21,33`、`AdventureFlow.cs:130`），
但只参与路线评分（`RouteScoring.cs:84-89`）与一行详情文案（`CraftingTargets.cs:108-111`）。
**局内完全看不到它**：HUD 标题只在非森林模式显示目标，而遗迹/洞窟也走森林探索模式（`AdventureFlow.UI.cs:19`、`AdventureFlow.cs:121-122`）。

设计：把"目标"升级为一份**可判定契约**，结构（概念模型，非最终代码）：

```
ObjectiveCard {
  objectiveId      // 稳定 ID，如 forest.gather / ruins.relic / cavern.vein
  goal             // 复用现有 ExpeditionGoal 三值，不新增枚举
  region           // ForestRuins / AncientRuins / CrystalCavern
  title, oneLine   // 一句话：做什么、为什么
  conditions[]     // 0..N 个可判定条件（AND）
  successRule      // 全部满足 + 成功撤离
  failureRule      // 死亡 / 主动放弃（与现有结算一致）
  progressModel    // 只读谓词 + 分母，用于 HUD 进度
  payoutChannel    // P1: none；P2: 既有 unlockedRecipes/specialRewards
}
```

**判定只允许读取这些已有信号**（审计已确认全部存在）：

| 信号 | 字段 | 语义 | 可防刷 |
|---|---|---|---|
| 本局所得材料 | 见 §3.1.1（GrossEarned） | 本局新获得、不含带入 | 是（带入的不计） |
| 宝箱开启 | `checkpoint.events[].used` + `kind==Treasure` | 真实开箱 | 是 |
| 击杀 | `checkpoint.enemies[].health<=0` + `forest.encounters[].type` | 真实死亡（精英/首领按布局类型判定） | 是 |
| 矿脉破坏 | `checkpoint.resources[].health==0` | 真实采集 | 是 |
| 机关链 | `c1:lever` / `c1:door` / `c1:archive` / `c1:hidden` 的 `used` | 真实交互 | 是 |

### 3.1.1 D-08 冻结：四个量不是同一件事（P1 修订）

原始设计把 `earnedRemaining` 直接当作"本局累计所得"。审计证明这是错的：
`AdventureRules.Spend`（`AdventureRules.cs:8-12`）**先扣 `earnedRemaining`**，而局内确有消费入口
（出口修复 `AdventureFlow.Exits.cs:32`、药水 `PlayerInventory.cs:64`、铭刻 `AdventureLoadout.cs:128`）。
因此必须区分四个量：

| 量 | 定义 | 现有来源 | 本局消费后 |
|---|---|---|---|
| **GrossEarned** | 本局**累计获得**，排除带入 | 产品无持久字段；P1 用运行时计数（内存，不落盘） | **不变**（单调不减） |
| **EarnedRemaining** | 本局获得、当前仍剩余 | `RunState.earnedRemaining[]`（v9 既有字段） | **下降** |
| **CarriedIn** | 出征带入、当前仍剩余 | `RunState.broughtRemaining[]`（v9） | earned 扣完后再扣它 |
| **Spent** | 本局消耗量 | 无持久字段 | 累加 |

产品自身强制的不变量：`broughtRemaining[k] + earnedRemaining[k] == checkpoint.materials[k]`
（`AdventureValidation.cs:49`）。

**冻结口径（P1 实现）**：

1. 目标进度一律使用 **GrossEarned**，`CarriedIn` 永不参与计数。
2. 进度**不因消费回退**：运行时计数只增不减。
3. 本批禁止新增存档字段，因此**跨进程**只能读到 `EarnedRemaining`。投影取
   `progress = max(运行时累计, EarnedRemaining)`：
   - 两项都 **≤** 真实 gross ⇒ **不可能凭空达成**（假阳性为零）；
   - 只有在"重进一个发生过消费的本局"时才可能**低报**（假阴性，且本批无任何发奖，代价为零）；
   - 求值结果带 `exact` 标记，低报场景标注 `basis=net`，HUD 不隐藏该事实。
4. **为什么不能精确**：`gross = earned + spent`，而 `spent` 与 `brought` 的初值都未持久化
   （v9 只存"当前剩余"），所以从既有字段无法反解 gross。这是零 schema 的硬边界，不是实现取舍。

**必须成立的反例（写入验收）**：

| 反例 | 期望 |
|---|---|
| 带 30 木材出征、不采集 | 采集目标进度 **0**（带入不计） |
| 采集 12 后消费 5（修复渡口/药水） | 本进程内进度仍为 **12**（不回退） |
| 同上并重启进程 | 进度显示 **7**，`exact=false`，且不判达成（保守下界，不重报） |

**两处设计修订（必须显式记录，不得静默改数）**：

1. **遗迹 Gather 8 → 6**。原设计按"遗迹箱 = 晶石 4–7 + 铁矿 1–3"估算，实际遗迹箱由
   `RuinsExploration.Chest` 直接生成 **Ore 1–3 + 晶石 1**（隐藏箱 3+2）。两箱上限仅 8，
   且需两箱都掷满，**8 不是确定可达**。改为 6：2 箱最低 4 + 2 名普通敌各 1 = 6，确定可达。
2. **森林寻宝删去"或带回 ≥1 件本局装备"分支**。双指标会让"进度"出现二义（1/3 箱 + 1 件装备算几步？），
   且装备掉落本身带随机。改为单一指标：宝箱 **3/6**。

**为什么每张卡都是"可达但不免费"**：
- 森林 12 单位 = 4 个矿点（最低 3/点），必须真的采集并拾取；
- 遗迹 6 单位 = 2 箱 + 2 击杀，必须推进到石柱广场与守护者大厅（无矿脉可刷）；
- 洞窟 3/4 矿脉 = 必须深入矿室与对岸；10 单位矿晶要 4 条脉（3 条最低只有 9）。

**不做的事**：不补矿点、不改掉落/产量/宝箱概率、不为不可达目标保留占位显示。


### 3.3 局内呈现（HUD 目标卡规格）

替换现有"目标卡"的一块（`PlayerHudPresenter.cs:46,100`），保持同位置、同尺寸，**不新增面板**：

| 行 | 内容 | 数据源 |
|---|---|---|
| L1 | 目标名 + 地区名（如"扫箱 · 森林"） | 目标卡 |
| L2 | **首个未满足条件**的进度（如"宝箱 2/3"、"材料 7/12"）；全部满足则"已达成 · 待撤离" | 只读谓词 |
| L3 | 一行"下一步"（如"最近：精英哨站 · 直线约 68 米"） | 实时枚举未开箱 / 存活精英 / 未采节点，取最近者 |
| 按钮 | 目标详情 / 取消（保留现有两个按钮语义） | 现有 |

> L2 只显示**一个**阻塞条件，是为了守住"进度 ≤12 字"且不产生二义（两个条件并列时读者无法判断还差什么）。
> L3 用**直线距离**而非导航距离：HUD 每 0.3 秒刷新，导航查询代价高；导航距离在 `M` 路线页给出。
> 目标卡区域由 250×92 调整为 250×124 以容纳三行，位置与锚点不变，不新增面板。

**关键改动只有一处**：`ActiveRun.goal` 目前局内不可见，需要在 HUD L1 显示它；且必须**按目标卡**而不是按 `mode` 分支，
否则遗迹/洞窟会继续被 `region` 分支覆盖。这是纯读取，零风险。

现在这些数据只以一段长文本出现（`CraftingTargets.cs:64-74`）。设计改为：

[路线] 按当前目标排序
① 精英哨站   目标匹配 0.82 · 风险 中 · 撤离：祭坛(免费,≈40m) · 评分 0.71   ← 推荐
② 归途祭坛   目标匹配 0.10 · 风险 低 · 撤离：本体            · 评分 0.44

### 3.5 达成 / 失败 / 关闭语义

| 事件 | 语义 | 结算表现 |
|---|---|---|
| 达成 | 契约条件全满足 **且** `AdventureRules.Success(outcome)`（`Extracted` / `TestChallengeComplete`） | 结算页"目标达成"角标；P1 不发任何收益 |
| 条件满足但失败 | 条件满足、结算未成功（死亡/放弃） | 角标写"条件已满足但未成功撤离"，**不判达成** |
| 未达成但撤离 | 正常结算，不清零收益 | "目标未达成"角标 + 差多少 |
| 死亡/放弃 | 与现有失败规则完全一致 | 不额外惩罚（避免双重惩罚） |
| 中途换目标 | **不允许**（D-02） | 局内只能看进度，不能改 |
| P1 收益 | **零**：不发材料/装备/货币，不写回执，不落盘（D-01=A、D-15=A） | 结算页仅文案与角标 |

## 4. 七武器与八扩展技能：从"能放"到"有构筑"

### 4.1 三层构筑模型

| 层 | 决策 | 时长尺度 | 现状 |
|---|---|---|---|
| L1 武器身份 | 我带哪把、备用哪把 | 跨局 | 已有 7 武器 + 手持/备用（`AdventureLoadout.cs:122-134`） |
| L2 技能槽 | 这局用哪 2 个技能 | 跨局（应持久化） | 已有 8+6 技能，但**选择不持久、无热键** |
| L3 词缀/铭刻 | 这把武器专精什么 | 跨局 | 已有 6 词缀 + 2 晶石定向铭刻（`AdventureLoadout.cs:124`） |
| L4 局内基础技能 | 这局滚出什么 | 单局 | 已有 6 种 × 无上限等级（`HeroProgression.cs`） |

**设计判断**：L1+L3 已经足够产生"构筑差异"，L2 只是缺少"被承认"（持久化 + 热键 + 取舍展示）。
因此**不需要新增技能**就能显著提升构筑感——这也符合 I3（不改冷却/伤害）。

### 4.2 七张武器角色卡（从现有参数推导，不新增数值）

| 武器 | 角色标签 | 依据（现有参数） |
|---|---|---|
| 长剑 | 稳定连段 / 低门槛 | `sword.triple` 3 段 ×0.65、`sword.circle` 3 脉冲 ×0.55，cd 8/11（`WeaponSkillExpansion.cs:9-10`） |
| 长枪 | 距离控制 / 蓄力穿刺 | `spear.charge` 1.2 倍 + 蓄力 0.85、`spear.sweep` 双向扇扫（:11-12） |
| 法杖 | 区域封锁 / 延迟爆发 | `staff.field` 真实接触后留场 3 脉冲、`staff.echo` 三段重瞄（:13-14） |
| 弓 | 远程贯穿 / 蓄力狙击 | `bow.pierce` 最多 3 目标贯穿、`bow.burst` 三段重瞄（:15-16） |
| 双刃 | 高频多段 / 反击窗口 | 六段 40%、反击需真实闪避成功才强化（`NewWeaponCombat.cs:10,43-44`） |
| 巨剑 | 蓄力破防 / 地面冲击 | 蓄力下劈 + 破防、冲击波被实体阻挡（:10,11） |
| 镰刀 | 群体收割 / 限速牵引 | 三段弧形收割、4.5m 牵引且 Boss 免疫（:10） |

用法：出征准备与角色页各显示一张"角色卡"，让玩家在**出发前**就知道这把武器解决什么问题。

### 4.3 技能槽：统一语义 + 持久化 + 热键（D-03）

现状三处不一致：
- 旧武器：槽 0 = 原技能，槽 1/2 = 扩展技能，`Selected` 0..2（`WeaponSkillPanel.cs:7`）；
- 新武器：只有 0/1 两槽（`NewWeaponCombat.cs:22`）；
- 两者选择都**不持久化**（`CombatSaveData.cs` 无对应字段）。

设计目标（按优先级）：

1. **语义统一**：对外统一为"2 个扩展槽 + 1 个基础动作"，新武器映射为"2 槽"，UI 文案不暴露内部差异。
2. **持久化**：按武器类型记住上次选择（7 条），读档/换场景/跨进程恢复后保持。
3. **热键**：`1/2` 切槽（仅在 `Field` 上下文、非 UI 打开时），保留 `F` 释放。
4. **取舍条**：每个槽显示 `冷却 / 前摇 / 段数 / 范围 / 蓄力`（数据全部来自 `WeaponSkillDefinition`，零新增）。

> 若 D-03 判定"存档 schema 冻结"，则 2 退化为 `GamePreferences` 本地配置（跨进程有效、不跨机器），
> 3/4 不受影响。这是本设计里**唯一**允许降级的点。

### 4.4 词缀方向（不新增词缀）

现有 6 条词缀已能表达三种意图，只需在 UI 上归组：

| 意图 | 词缀 | 适合 |
|---|---|---|
| 输出 | 锐利（+15% 伤害）、猎首（<35% 生命 +30%）、聚能（+25% 主动伤害 / 冷却 +1s） | 巨剑、长枪、弓贯穿 |
| 节奏 | 疾风（普攻间隔 −18%）、回响（技能范围/散射 +25%） | 双刃、弓连射、法杖符阵 |
| 续航 | 汲取（野怪伤害 6% 回血） | 镰刀群怪、长枪扫锋 |

铭刻规则保持不变（2 晶石，替换第一词缀；金/红保留第二条）。设计只加"意图标签"，让玩家知道自己在凑什么。

### 4.5 组合推荐（只推荐，不改数值）

出征准备页给 3 条"组合提示"，全部由现有数据推导：

- 远程 + 近战（弓/法杖 + 巨剑/双刃）：覆盖"开怪距离"与"贴身突发"。
- 双远程（弓 + 法杖）：最大化安全距离，但共用冷却导致爆发窗口重叠（真实代价）。
- 双近战（巨剑 + 镰刀）：清群强、无法处理高处/远程，需要靠翻滚接近。

**不做**"组合加成"——那会改数值。

## 5. 装备成长与制造

### 5.1 三条追求线 + 一条保底线

| 线 | 确定性 | 现有机制 | 玩家语言 |
|---|---|---|---|
| 品质线 | 完全确定 | 29 条配方，紫/金/红三档 | "我要做一把金弓" |
| 词缀线 | 半确定 | 掉落随机 1–2 条 + 2 晶石定向铭刻 | "我要把这条猎首刻上去" |
| 藏品线 | 一次性确定 | 6 个特殊奖励（钥/残卷/印/遗镰/守护者初誓/晶脊初誓） | "我还差哪个藏品" |
| **保底线** | 确定 | 遗迹守护者必掉紫装、洞窟 Boss 必掉紫新武器 | "打不过就先去拿保底" |

设计判断：**"持续装备追求"不需要单件升级**，三条线已经提供 3 种不同节奏的追求；
真正缺的是"把三条线摊开给玩家看"，以及"制造后的下一个目标"。

### 5.2 成本梯度（用现有公式计算，不改）

`n = 品质 + 1`，成本 = 木 `2n` / 石 `n` / 矿 `2n` / 晶 `n−1` / 核心 `max(0,n−3)`（`CraftingTargets.cs:12`）：

| 品质 | 木 | 石 | 矿 | 晶 | 核心 | 采集节点当量* | 相对紫 |
|---|---|---|---|---|---|---|---|
| 紫（n=3） | 6 | 3 | 6 | 2 | 0 | ≈ 3.3 点 + 2 晶 | 1.00× |
| 金（n=4） | 8 | 4 | 8 | 3 | 0 | ≈ 4.4 点 + 3 晶 | 1.33× |
| 红（n=5） | 10 | 5 | 10 | 4 | 2 | ≈ 5.6 点 + 4 晶 + 2 首领 | 1.67× |

\* 采集点均值 4.5 单位/点（3–6，`AdventureResource.cs`）。一局森林清完 42 点约 189 单位，远超单件需求——
**瓶颈不是材料，是"决定做哪件"和"带得走多少"**。这正是目标系统要解决的问题。

### 5.3 目标闭环：目标 → 缺口 → 路线 → 制造 → 下一目标

现有 `CraftingTargets` 已经实现了"缺口"与"推荐"（`CraftingTargets.cs:24-83`），但制造成功后立即清除目标（:47-48）。
设计补最后一步——**下一目标建议**，规则（纯规则，无随机）：

```
若 当前无目标:
  1) 若 有 pending 未领取 → 建议"回营领取"
  2) 若 有缺失配方（Advanced 且未 Knows） → 建议"先解锁配方 X（缺 …）"
  3) 若 装备最弱槽位（Attack/Defense 最低）可提升一档 → 建议"做 <槽位> <品质>"
  4) 否则 → 建议"去 <地区> 完成 <目标卡>"
```

"最弱槽位"用 `AdventureLoadout.Attack/Defense` 与各槽 `GearItem.Attack/Defense` 现算（`AdventureLoadout.cs:18-21`）。

### 5.4 结算页"下一局三件事"

现有结算页只列得失（`AdventureFlow.UI.cs:54-71`）。追加一块（同页，不新增页面），三条全部来自现有数据：

| 条目 | 文案模板 | 数据源 |
|---|---|---|
| 缺口 | "还差 木 4 / 晶 1 就能做金弓" | `CraftingTargets.Needs` |
| 未竟 | "森林还有 2 个宝箱点没去（精英哨站 / 湖岸）" | 结算前的 `RouteScoring` 快照 |
| 下一步 | "建议下次：森林 · 扫箱（3/6）" | 5.3 规则 |

> 注意：结算发生在世界卸载后，`RouteScoring` 无法再跑。因此"未竟"必须在 `LockOutcome` 前抓一份只读快照
> （`AdventureFlow.cs:180-185`），随结算记录展示；不写入存档则仅本页可见（P1 足够）。

## 8. 信息架构与文案原则

### 8.1 信息层级（三层，禁止越级）

| 层 | 位置 | 内容 | 字数上限 |
|---|---|---|---|
| L1 常驻 | HUD 右上 | 目标名 + 进度 + 一行下一步 | 目标名 ≤ 8 字，进度 ≤ 12 字 |
| L2 一键 | `M` 路线 / 目标详情 | Top3 路线卡、缺口明细 | 每卡 ≤ 3 行 |
| L3 按需 | 出征准备 / 结算 | 完整规则、三件事 | 可长，但必须分块 |

### 8.2 文案原则

1. **动词开头**：`扫箱`、`掘脉`、`试锋`，不用名词堆叠。
2. **给数字**：`2/3` 而不是"还差一些"。
3. **给方向**：`最近未开箱：精英哨站 · 约 68 米`，不只说"还有箱子"。
4. **说人话**：内部术语（`TARGET_MISMATCH`、`NO_USABLE_EXIT`）必须映射为玩家语言。
5. **不撒谎**：文案里的数字必须来自实时状态，不得用静态模板假装进度。

## 10. 设计自检

| 检查 | 结论 |
|---|---|
| 是否重复实现了已有系统？ | 否。路线评分/缺口/配方/结算/引导全部复用（审计 §8） |

| 是否能在零 schema 下先落地一半？ | 是。P1 全部为只读呈现 |
