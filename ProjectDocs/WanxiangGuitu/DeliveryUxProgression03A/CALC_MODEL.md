## 1. 归一化与适用范围

所有伤害以 **P = hero.AttackPower** 归一化。`ThirdPersonHero.cs:22`：

```
P = attackDamage(25) + Equipment.AttackBonus + Progression.AttackBonus
```

`Equipment.AttackBonus → AdventureLoadout.Attack = Active.Sum(i => i.Attack) + 胸挂/背包 attackBonus`（`HeroEquipment.cs:15`、`AdventureLoadout.cs:22`）。
因为本文所有指标都是 **P 的比值**，装备品质与等级只做整体缩放，**不改变 η / B 的排序**。

适用对象：7 套普攻、4 个旧武器槽 0 内置技能、14 项扩展技能 = 25 行（`SKILL_VALUE_MODEL.csv`）。
**不适用**：品质专属追加弹体、词缀乘算、敌人护甲/减伤、暴击、伤害溢出、控制收益 —— 这些单独列在 §6，不折算成倍率。

## 2. 符号与公式

| 符号 | 含义 | 单位 | 来源 |
|---|---|---|---|
| `m_p` | 第 p 次 Release 的伤害系数 | ×P | `WeaponSkillDefinition.power` / 各 Motor 的 factor |
| `D` | 一次完整施放的伤害总额 `Σ m_p` | ×P | 源码参数求和 |
| `W` | 窗口：从施放开始到动作结束，期间不能普攻 | s | 见 §2.1 |
| `C` | 冷却：从施放**开始**计时 | s | `PrepareExpanded` / `UseSkill` / `SetNewCooldown` |
| `R` | 该武器纯普攻的持续输出率 | ×P/s | `Σ m_basic / cycle` |
| `N` | 场景中可命中的不同目标数 | 个 | [疑] 假设，见 §4 |
| `cap` | 该形状单次 Release 的覆盖上限 | 个 | [疑] 假设，见 §4 |
| `H` | 命中可靠性（弹体遮挡 / 瞄准 / 蓄力被打断） | 0–1 | [疑] 假设，见 §4 |

### 2.1 窗口 W 的源码时序（不手填，由脚本按参数算出）

| 类型 | 公式 | 依据 |
|---|---|---|
| 旧武器槽 0 | `W = 0.50`（`ActionDuration(hero.AttackInterval)`；技能不吃 `SpearCadence`） | `AdventureCombat.cs:62,74,79` |
| 旧武器扩展（非蓄力） | `W = startup + (pulses−1)×gap + 0.22`（最后一段后 `finish=Time.time+.22f`） | `WeaponSkillExpansion.cs:48-49` |
| 旧武器扩展（蓄力） | `W = charge + startup + 0.22`（先等 charge，再等 startup） | `WeaponSkillExpansion.cs:46` |
| 新武器技能 | `W = startup + Σ段间隔 + 收招`，逐 Motor 读 `end` 赋值 | `NewWeaponCombat.cs:43-44`、`GreatswordCombat.cs:5-6`、`ScytheCombat.cs:5-6` |

### 2.2 四个输出指标

```
D(N,H) = (Σ m_p) × min(N, cap_skill) × H_skill
R(N)   = (Σ m_basic / cycle) × min(N, cap_basic) × H_basic
G      = D − R × W                         净收益（一次施放相对"同窗口一直普攻"）
B      = D / (R × W)                       爆发系数（窗口内伤害效率）
E      = (D + R × max(0, C − W)) / C       一个完整冷却周期的平均输出率
η      = E / R                             相对纯普攻的持续效率
```

**[推] 核心恒等式**（代入即消元）：

```
η = 1 + (B − 1) × W / C
```

这条恒等式决定了整个 03A 的调整策略：

1. **B < 1 时，任何冷却调整都无法修复** —— 降低 C 只会把 η 压得更低（因为 `(B−1)<0`）。必须先增大 `D` 或减小 `W`。本批 14 项里有 **8 项 B<1**，这是「扩展技能没人用」的真正原因，不是倍率差。
2. **B > 1 时**，降低 C 会放大收益，但放大幅度受 `W/C` 限制：长窗口技能即使 B 很高，η 也只能贴近 1。所以 **η 不可能被拉到很高，也不需要被拉到很高**。
3. `W/C` 是结构常数：槽 0 是 `0.5/7 ≈ 0.071`，扩展技能是 `0.56–1.52 / 7–11 ≈ 0.05–0.19`。这就是为什么「把扩展技能倍率对齐槽 0」是错误目标 —— 两者的窗口成本根本不同。

## 3. 三条目标带（禁止一刀切）

| 带 | 适用 | 门槛 | 理由 |
|---|---|---|---|
| **T1** | 无独占机制的纯伤害技能 | `B ≥ 1.10` 且 `η ≥ 1.01` | 没有任何机制补偿，就不能比"一直普攻"更差 |
| **T2** | 有独占机制（360° / 贯穿 / 留场 / 分时重瞄 / 破防 / 六段 / 宽弧 / 蓄力 / 双扇 / 地面波） | `B ≥ 1.00` 且 `η ≥ 1.00`，并在**至少一个已定义场景**优于槽 0 | 机制本身是收益，允许 η 贴近 1 |
| **T3** | 条件触发 / 纯控制（`twin.counter`、`sc.pull`） | **η 不适用**，另设验收口径 | `sc.pull` 伤害恒为 0，η 恒 <1；`twin.counter` 常态 0.65× 是"未触发强化"的固有代价 |

**[推] 明确禁止**：把 AOE、贯穿、控制、前摇、恢复、命中率折成一个"等效倍率"再统一对齐。
本文把它们保留为独立列（`cap` / `mech` / `W` / `H` / `src`），并在 §6 单独评估。

## 4. 假设与敏感度（必须标注 [疑]）

| 假设 | 取值 | 性质 |
|---|---|---|
| `cap_basic` | 长剑 3 / 长枪 2 / 法杖 2 / 弓 1 / 双刃 2 / 巨剑 4 / 镰刀 4 | [疑] 由形状角度与半径推断，**无 Player 实测** |
| `cap_skill` | 逐技能 1–5，见 `SKILL_VALUE_MODEL.csv` 的 `cap` 列 | [疑] 同上 |
| `H` 主模型 | 全部 = 1.0（全命中理论上界） | 避免把猜测写进主结论 |
| `H` 敏感度 | 近战恒 1.0；弹体/蓄力/留场/控制类取 `{1.0, 0.8, 0.6}` | `SENSITIVITY.csv`（162 行） |
| `N` 敏感度 | `{1, 3, 5}` | 同上 |
| 冷却期内行为 | 施放结束后一直普攻 | 保守下界；实际可交替两个技能，收益更高 |

**[推] 一个反直觉但重要的结果**：当技能与普攻的 `cap` 相同、且 `H` 相同时，`η` 与 `N` **无关**（两者按同一比例缩放）。
也就是说 **AOE 只有在「技能覆盖目标数 > 普攻覆盖目标数」时才产生净收益**。
例如 `sword.circle`（360°/3.1m，`cap=5`）对长剑普攻（75.5°/1.8m，`cap=3`）：在 N=5 的包围场景才真正优于普攻；在 N=1 时它因为 `W=1.50s` 反而更差。这正是"不能只看倍率"的量化证据。

## 5. 模型算出的三个结构性发现

### 5.1 七把武器的普攻 DPS 是两个梯队，不是一个

| 梯队 | 武器 | R (×P/s) |
|---|---|---|
| 高 | 长剑 / 法杖 / 弓 | 2.000 |
| 中 | 长枪 1.923、双刃 1.878 | — |
| **低** | **巨剑 1.000、镰刀 1.000** | — |

**[源]** 巨剑 `1.05× / 1.05s`、镰刀 `0.80× / 0.80s`（`GreatswordCombat.cs:3`、`ScytheCombat.cs:3`）。
**[推]** P1/P1C 报告里"巨剑单发最高"是对的，但**持续输出只有长剑的一半**。它们靠 65°/85° 扇形与 2.6/3.0m 距离换多目标覆盖，不是靠倍率。任何"把巨剑倍率调到和长剑一致"的做法都会破坏这个交换。

### 5.2 8/14 扩展技能 B<1 —— 严格劣于"同窗口一直普攻"

| 技能 | 现状 B | 现状 η | 主因 |
|---|---|---|---|
| `sword.circle` | 0.550 | 0.939 | `W=1.50s`（gap 0.48×2）吃掉收益 |
| `sc.pull` | 0.000 | 0.932 | 0 伤害（T3，不适用 η） |
| `twin.counter` | 0.666 | 0.978 | 常态 0.65×（T3，强化后才成立） |
| `bow.pierce` | 0.701 | 0.959 | `W=1.52s`（蓄力 1.0 + 0.3 + 0.22） |
| `staff.echo` | 0.711 | 0.963 | `W=1.16s` 三段分时 |
| `gs.wave` | 0.731 | 0.965 | `W=1.30s` 且单发 0.95× |
| `spear.charge` | 0.881 | 0.983 | `W=1.31s`（蓄力 0.85 无保护） |
| `bow.burst` | 0.907 | 0.991 | 0.55× 三段总量偏低 |

其余 6 项 B 只落在 `1.05–1.65`，η 落在 `1.004–1.044`。
而 4 个旧武器槽 0 的 η 是 `1.071 / 1.107 / 1.086 / 1.357` —— **扩展技能没有一项达到对应槽 0**。

### 5.3 品质缩放不对称，是比倍率更根本的断层

| 槽 0 | 白 D | 红 D | 倍率增长 |
|---|---|---|---|
| `sword.whirl` | 2.00 | 4.25 | ×2.13 |
| `spear.thrust` | 2.40 | 4.20 | ×1.75 |
| `staff.meteor` | 2.20 | 3.80 | ×1.73 |
| `bow.rain` | 6.00 | 10.80 | ×1.80 |

**[源]** `AdventureCombat.cs:186-189`（`q>=2` 追加剑气/穿刺余波、`q>=3` 侧球、`q>=4` 枪芒/爆裂；`BowHalfCount` 5→7→9 箭）。
**14 项扩展技能全部不吃品质**（`WeaponSkillDefinition` 无 quality 字段；`WeaponSkillExpansion.Release` 不读 `source.quality`）。
**[推]** 玩家装备越好，槽 0 越强、扩展技能原地不动 —— 差距随进度**单调扩大**。红弓 `bow.rain` 的 η 达 1.700，而 `bow.burst` 仍是 0.991。
**因此 03A 不追平倍率**：让扩展技能在「独占场景」里成立，并把品质专属补齐到三把新武器（§5 品质提案），而不是给 14 项都加品质加成。

## 6. 不折算成倍率的六个维度

| 维度 | 本文的表达 | 为什么不能折算 |
|---|---|---|
| AOE | `cap_skill` vs `cap_basic`、`half_angle_deg`、`reach_m` | 收益只发生在"技能覆盖 > 普攻覆盖"的场景，依赖敌群密度 |
| 贯穿 | `bow.pierce` 最多 3 个不同目标（`SkillPhysicalEffects.cs:14`）、`gs.wave` 8m 行程 | 依赖敌人排队，不是伤害系数 |
| 控制 | `gs.cleave` 破防 0.75s、`sc.pull` 牵引 1s；**Boss 与 ForestBoss 免疫**（`EnemyWeaponControl.cs:4`） | 价值 = 取消一次敌人攻击，与血量无关 |
| 前摇 / 恢复 | `W` 拆分到 `startup / gap / charge / recovery` | 决定「会不会被打断」，不决定伤害 |
| 实际命中率 | `H` 敏感度列；弹体要过 `Sight`，蓄力会被打断 | 无法从源码定值，必须 Player 实测 |
| 场景切换成本 | `Select(slot)` 每局重置（D-03 未授权持久化） | 构筑成本，不是战斗数值 |

## 7. 复算与自检

```bash
python Evidence/Tools/build_balance_model.py --out .
# 应输出 rows: skill_value_model=25 before_after=40 sensitivity=162 focus=8
# model-run.json 记录参数表 SHA 与四张 CSV 的 SHA
```

自检不变量（任一不成立即模型有误）：

1. `η = 1 + (B−1)×W/C`（CSV 保留 4 位小数，逐行误差 < 5e−5；实测最大 4.56e−05）；
2. `B<1 ⟺ η<1`（T3 除外）；
3. `η` 对 `N` 不变，当 `cap_skill == cap_basic` 且 `H_skill == H_basic`；
4. 提案后 T1/T2 共 12 项全部 `PASS`，T3 两项 `N/A`；
5. 所有提案只改 `L1` 常量，`D/W/C` 之外的判定参数一行未动。
